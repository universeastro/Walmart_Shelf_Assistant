### 1.3 C-01 的实测依据

两版口径都有工件支撑，但**支撑强度不同**：

- 旧口径（追加）：用户通过选项明确答复；且 `文件/02/B模板.xls` 自身结构即追加累积产物
  （R286–R288 三行全空，把数据切成 R2–R285 与 R289–R696 两块，第二块起点
  `289 = 285 + 4`，与 `docs/APPEND_VERIFICATION.md` 的「末行 L 的 L+4」规则逐字吻合）。
- 新口径（替换）：依据 `QQ20260911-163801.mp4`。**该视频未被证明能支撑「清除到 R696」。**

**Claude 复核结论（2026-09-11 17:45，抽取两支视频关键帧后）：**

- 视频里被操作的目标文件 `9.9自定义.xls`（即后来的 `文件/02/B模板.xls`，
  标签页 `Sheet1|Sheet2|Sheet3`、`A1=SKU`、`B1=平台SKU` 均吻合），
  **在粘贴前第 5 行以下就是空的**（A2–A4 有 3 行残留，A5 起全空）。
- 视频只演示了**往一个空目标里从第 2 行粘贴为数值**这一件事。
  空目标上「从第 2 行粘贴」与「追加写入」**是同一个动作**，无法据此区分两种语义。
- 因此：视频**支持**「粘贴为数值、起点第 2 行」，
  **不支持**「清除 R308–R696 的既有数据」——那部分目标是空的，无从演示。
- 旁证：`文件/02/QQ20260911-164848.mp4`（16:48，**比 Codex 引用的那支更晚**）
  全程未被 `HANDOFF.md` 提及。两支持平：同分辨率 1918×1038、同长度约 34 秒。

**对 `文件/02/B模板.xls`（696 行真实数据）实测 `-Profile Req02` 的后果：**
`$clearEnd = max(existingLastRow=696, 2+306-1) = 696` → `ClearContents('A2:B696')` →
**原有 688 个唯一 SKU 中 687 个在输出里消失**（仅 1 个与本次数据巧合重叠而幸存）。
两个原始文件的 md5 均未变，副作用只落在输出副本上。

### 1.4 生效处置

因为 C-01 是**不可逆的数据破坏**，且新证据（§1.3）反而削弱了新口径的依据，
在用户明确改口之前，按**非破坏性默认**执行：

- **默认 `追加`**：保留既有数据，符合用户唯一一次明确答复，且万一判错可重跑修正。
- **`替换` 作为显式开关**，不由默认路径触发。
- `PROJECT.md` 验收标准分别覆盖默认追加与显式替换，避免以实现细节自证。

> 判错代价不对称：想要追加却做了替换 → 692 条记录永久丢失；
> 想要替换却做了追加 → 多出旧行，重跑一次即可。故默认取追加。

**用户如需替换语义，一句话即可改回**（本项登记为 C-01，写明裁决人即可生效）。

## 2. 分歧升级规则

分工协议只要求「记协调项」，没有规定**记完之后怎么办**。补充：

1. 双方对同一事实得出不同结论时，**先各自写明依据（文件名/行号/命令/输出）**，不做让步式折中。
2. 满足以下任一条 → **必须升级用户**，不得由任一方自行收口：
   - 结论涉及**不可逆的数据变更**（删除、覆盖、清空）；
   - 新结论**推翻用户已经明确答复过的**口径；
   - 双方依据都成立但互斥。
3. 升级期间该条目状态置 `阻塞`，相关实现**不得动工**。已动工的必须挂起并说明进度。
4. `TASKS.md` 的「主负责人」身份**不构成**对第 2 条三项的裁决权。

> C-01 就是反例：视频（新证据）推翻了用户的选项答复（旧决策），
> 由实现者单方采信新证据并合入 `PROJECT.md`/`TASKS.md`，全程未升级。

## 3. 冻结窗口协议

**问题：** 审查方只能靠 `ls --time-style` 猜对方是否还在写。实测 Codex 的写入是连续的
（17:21 → 17:33 → 17:34 → 17:36 → 17:38 → 17:40），5 分钟阈值基本永远不满足，
审查永远进不了场。

**规则：**

- 实现方本轮写入结束，必须在 `HANDOFF.md` 追加一行独立标记：
  `## 本轮写入结束 2026-09-11 17:40`，其后**不得再改任何被跟踪文件**。
- 审查方**只在看到该标记后进场**；未见到标记一律不动手（不校验、不提交、不改文件）。
- 审查方开始审查时同样追加 `## 审查开始 <时间>`；审查期间实现方不得写入。
- 审查方给出结论后追加 `## 审查结束 <时间>`，控制权交回实现方。
- 紧急修正可打断冻结，但必须补记打断原因。

## 4. 验证独立性

**验证脚本由实现者写是可以的；断言由实现者定是不可以的。**

- 每条断言必须能指回**需求文档原文或用户决策记录**，不得引用实现里的字面量/常量。
- 反例（现存）：`tests/verify_req02.ps1:22`
  ```powershell
  if ($result.writeStartRow -ne 2 -or $result.mappings.Count -ne 2) { throw ... }
  ```
  `2` 抄自实现的 `$targetInfo.DataStart`。**语义即使判错（§1.3 实测确实丢了 687 条），
  该测试照样通过**——它验证的是「实现等于实现」。
- 该文件由实现方拥有，Claude **不代改**；已登记为待修项。
- 验证脚本涉及写入语义、清除范围、行数这类**契约级断言**时，需由非实现方复核后才算数。

## 5. 回归门槛

- 任何提交前，**主线（B01）全套验证必须全绿**：`tests/verify_*` 中与主线相关的全部，
  以及 `AGENTS.md`「改完必须验证」一节列出的命令。
- 改动触及单元格格式时追加 `tests/verify_alignment.ps1`；触及 OOXML 部件时追加
  `tests/compare_ooxml.py`。
- 本仓库**无 CI**（已确认无 `.github`、无任何流水线配置），全靠人工执行。
  因此提交信息中必须**逐条列出实际跑过的命令与退出码**，未跑的必须写进「未覆盖」一节。
- 支线改动不得使 B01 行为变化；`-Profile` 默认值必须保持 `Mainline`。

`HANDOFF.md` 是**双方共写**的（实现方拥有，审查方追加），但没有写过规则，目前靠运气。

  「更正 <章节名>」，并在原文处加一行指针，不直接删除。
- 每节标题必须带日期与作者：`## 2026-09-11 Claude ...`。

- **`HANDOFF.md` 出现互相矛盾的两节时，以带日期的后一节为准**，且必须在前一节加指针。
