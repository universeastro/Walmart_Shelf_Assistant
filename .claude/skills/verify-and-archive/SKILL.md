# Codex 改动后的校验与存档

Codex 产出的代码**必须经过独立校验才能进入历史**。自己写自己审没有意义——
本流程的价值就在于用**不同的眼睛**跑**可执行的证据**，而不是重读一遍代码说「看起来没问题」。

## 核心规则

> **校验不通过，绝不 commit，绝不 push。**

历史里只保留已验证的状态。未通过校验的改动留在工作区由 Codex 修，
不要为了「先存一下」而提交——那会让「每个提交都是已验证的」这个性质失效，
而这是本仓库历史唯一的价值。

---

## 第 0 步：确认改动范围

```bash
git status --short              # 未提交的改动
git log --oneline origin/main..HEAD   # 已提交但未推送的
```

两者**都为空** → 没有新工作，直接报告「无新改动」并结束，不要为了做事而做事。

非空 → 记录基线提交（`git rev-parse HEAD`）**和改动文件的哈希**，后续所有校验
针对这个范围。哈希是第 5 步复核的依据，**现在就记下来**：

```bash
md5sum app.py excel_mapper.ps1      # 只列本次改动的文件
```

**先看时间戳**：

```bash
ls -la --time-style=+%H:%M *.py *.ps1 *.md
```

> ⚠️ **禁止使用 `git add -A`。** 本仓库有并发写入者（Codex），
> 你编辑文件和提交之间，它可能已经改了别的文件——`-A` 会把未经验证的改动
> 一起提交。**必须显式指定本次要提交的文件**：
> `git add <文件1> <文件2>`。这条是实际踩过的坑，见
> `docs/CODE_REVIEW.md` 的「本次更新的过程失误」。

如果最新写入在**几分钟内**，Codex 很可能还在写。此时不要开始校验——
你会对着一个移动的目标做判断。先报告「Codex 可能仍在写入」并等待。

## 第 1 步：功能测试（必做，不可跳过）

跑 `verify-mapping` skill 的脚本：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass `
  -File .claude/skills/verify-mapping/scripts/verify_mapping.ps1 `
  -SourcePath tests/fixtures/A_sample.xls `
  -TargetPath 文件/B模板01.xlsx
```

退出码：`0` 全对 / `1` 有字段不一致 / `2` 源数据压根没写入。

**注意**：
- 若 `excel_mapper.ps1` 的映射表有改动，**必须先更新 `verify_mapping.ps1` 里的 `$Pairs`**，
  否则是拿旧契约校验新实现，会得出假阳性。
- **不要只依赖合成样本。** 夹具只有一行数据，会掩盖性能与多行逻辑问题。
  见第 3 步的补充测试。

## 第 2 步：接口与边界测试

合成样本跑通后，补齐这几类（按改动内容取舍）：

1. **歧义与降级路径**：`fallback-column` 的映射（当前是 `E -> Variant Group ID`）
   是否仍指向正确列？源表列序变动时会怎样？
2. **空输入**：空模板（`文件/A模板01.xls`）应返回 `rowsRead: 0` 而非报错。
3. **多行输入**：**已有现成工具，直接跑**（不要再手工造夹具）：

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File tests/verify_multirow.ps1 -Rows 372
   powershell -NoProfile -ExecutionPolicy Bypass -File tests/verify_multirow.ps1 -Rows 5 -BlankAt 3
   ```

   退出码 `0` 全对 / `1` 有失败（逐条打印期望值与实际值）。
   它自己生成夹具、跑映射器、逐格比对，断言由映射器的 JSON 契约驱动，
   改映射表也不会变成假阳性。**`-Rows 372` 是真实规模。**
4. **边界**：源表数据行多于模板可容纳行数时会怎样？

## 第 3 步：代码审查（改动部分）

**读 diff，不读全文**——全文通读只在首次接手或大重构时做：

```bash
git diff <基线提交> -- <改动的文件>
```

审查重点（这些是本项目踩过的坑，不是通用清单）：

- 是否有**按列字母兜底**的映射新增/改动？列字母不可信（见 `docs/VERIFICATION_REPORT.md` 3.2）
- 表头定位逻辑是否引入新的**硬编码列号/行号**
- 是否新增了**重名叶子表头**的目标字段（模板中 `unit`、`measure` 各重名 5 次）
- 是否碰了 `$columns = @{}`（改成 `[ordered]` 会炸，见 `AGENTS.md` 约束 5）
- 新增 `.ps1` 是否带 UTF-8 BOM

## 第 4 步：格式保留抽查（改动涉及写入逻辑时）

用第 1 步的输出文件，对比模板与输出的 OOXML 部件。

> **判据是 sqref 覆盖范围，不是规则数。** Excel 会合并条件相同的相邻列规则
> （实测 48 条 → 43 条），数量变少是正常的，**不是 bug，不要去「修」**。
> 详见 `docs/VERIFICATION_REPORT.md` 2.2 节。

**注意**：工作表文件编号会变（`sheet2.xml.rels` → `sheet3.xml.rels`），
必须**按工作表名称对齐**再比对，否则是在比两个不同的工作表。

## 第 5 步：判定与存档

### 全部通过 → 先复核哈希，再存档推送

> ⚠️ **提交前必须复核哈希。** 第 0 步的时间戳检查是**必要但不够的**。
>
> 本项目实际发生过：第 0 步看到工作区干净，随后 Codex 在 **14:28:59** 写入新版本——
> 恰好落在校验进行的过程中。结果是「已验证通过」的结论，对应的其实是一份当时
> 还不存在的代码。全靠提交前手工复核哈希才发现。
>
> ```bash
> md5sum <改动的文件>          # 必须与第 0 步记录的基线逐字节一致
> ls -la --time-style=+%H:%M:%S <改动的文件>
> ```
>
> **不一致 → 立即停止，回到第 0 步重来。** 不要因为「刚才验过了」就跳过。
> 校验跑得越久，这一步越不能省。

提交信息要写清楚**改了什么**和**验证了什么**，让下次审查能快速定位：

```bash
# ⚠️ 显式列出文件名，不要用 git add -A（见第 0 步的红线说明）
git add <文件1> <文件2>
git commit -F - <<'EOF'
<类型>: <一句话说明>

Codex 本轮改动：
- ...

验证（Claude，独立复跑）：
- 映射正确性：<结果>
- 边界与多行：<结果>
- 格式保留：<结果>
- 未覆盖：<如实列出没测到的>

Co-Authored-By: Claude Code <noreply@anthropic.com>
EOF
git push origin main
```

**「未覆盖」一节必须如实写。** 没测到的部分不写，下一个读历史的人会误以为测过了。

### 有失败 → 不提交，报告

1. 写清楚**失败的具体字段/行/列**，附原始输出
2. 给出**最小复现步骤**
3. 指明怀疑的代码位置
4. **不要自己动手修**——修是 Codex 的职责，避免两边同时改同一份代码产生冲突

## 常见误判（别浪费时间在这些上）

以下都**不是** bug，本项目都实测确认过：

| 现象 | 真相 |
|---|---|
| 条件格式规则数变少（48→43） | Excel 合并了条件相同的相邻列规则，覆盖等价 |
| `rowsRead: 0` | 空模板的正常返回，不是缺陷 |
| 输出文件几乎每个 OOXML 部件都不同 | Excel 重新序列化了整个包，非定向补丁；需看的是部件有无**丢失** |
| 映射出现 `fallback-column` | 不一定错，但**值得人工确认**——它意味着没有名称校验 |

## 推送（本仓库特有）

本机直连 github.com 超时，**必须走代理**。仓库级代理已配好；
若换机器或代理未生效，报错是 `Recv failure: Connection was reset`：

```bash
git config --local http.proxy http://127.0.0.1:7890
git config --local https.proxy http://127.0.0.1:7890
```

## 触发方式（2026-09-10 与用户确认）

**没有钩子能感知「Codex 操作完成」**——hooks 只能挂在我自己的生命周期事件上，
Codex 是另一个进程，它的状态我看不到。所以采用的是**定时轮询 + 通过后自动推送**：

- 定时任务 `1cd84df6`，cron `3,13,23,33,43,53 * * * *`（每 10 分钟，避开整点）
- **只有本会话存活且空闲时才会触发**；状态持久化在 `.claude/scheduled_tasks.json`
- 复发任务 **7 天后自动过期**，到期需重建
- 轮询的廉价路径：`git status --short` 与 `git log origin/main..HEAD` 同时为空 → 一句话结束，不做任何事

轮询会被仓库里的游离文件干扰，所以 `.gitignore` 必须挡住
`.claude/scheduled_tasks.{json,lock}` 与 `/out_*.xlsx`（手动试跑产物）。
**若哪天 `git status` 里冒出这类文件，说明忽略规则失效——报告它，不要顺手提交它。**
